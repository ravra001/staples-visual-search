Request flow — one photo search

The pipeline is identical in both environments; only the providers behind the embed / classify / rank steps change.

  1. 1UploadUser picks a photo; the browser POSTs it to /api/visual-search (validated + size-capped).
  2. 2EmbedImage → normalized vector (heuristic, local CLIP, or Vertex AI). Runs in a threadpool.
  3. 3ClassifyNearest-centroid → predicted category + confidence (the “Detected:” chip).
  4. 4RankVectorized cosine (M · q) vs the pre-embedded index; scoped to the category when confident. Top-K.
  5. 5HydrateBatch-fetch product rows for the winning SKUs; attach the % match.
  6. 6RenderChip + product cards; weak (below-threshold) matches collapse, or a “no strong matches” state.

GCP production pipeline (pgvector target)

The fuller production design. The catalog and its vectors live together in Cloud SQL + pgvector, embedded by Vertex AI and kept fresh by a standalone pipeline. Similarity is computed in the database; query embeddings are logged asynchronously for relevance tuning — never on the critical path.

Notes on scale

Precomputed index

Catalog embeddings are computed once and cached, not on every request. At tens of thousands of SKUs this becomes a one-time offline build step (cache vectors to disk / a table), so server startup stays instant.

Brute-force is fine — until it isn't

Cosine over an in-memory matrix is sub-millisecond for thousands of SKUs. Only when the catalog reaches large scale do you graduate to Vertex AI Vector Search / Matching Engine — the ranking interface doesn't change.

Dimension-agnostic

59-dim heuristic, 512-dim CLIP, or 1408-dim Vertex vectors all flow through the same vectorized _rank() (one M · q matmul) — swapping the model changes nothing downstream, only the fingerprint on the cached index.
