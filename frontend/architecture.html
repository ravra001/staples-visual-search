Visual Search — Architecture

This app runs two ways: fully offline on a laptop (DATA_BACKEND=memory), or on Google Cloud — Cloud Run + Cloud SQL/pgvector — which is how it's actually deployed today, not a future plan. The one piece genuinely still ahead: swapping local CLIP for Vertex AI Multimodal Embeddings has never been tested or benchmarked in production (see the callout below).

Request flow — one photo search

The pipeline is identical in both environments; only the providers behind the embed / rank steps change. Text refinement, Find Similar, and Shop the Room all extend this same flow rather than introducing separate ones — see How It Works for how each one reuses these steps.

  1. 1UploadUser picks a photo; the browser POSTs it to /api/visual-search (validated + size-capped).
  2. 2EmbedImage → normalized vector (local CLIP today; Vertex AI is a coded, untested alternative). Runs in a threadpool.
  3. 3ClassifyNearest-centroid → predicted category + confidence (the "Detected:" chip).
  4. 4RankVector comparison (in-memory matmul, or a pgvector query) vs the catalog; scoped to the category when confident. Top 48.
  5. 5HydrateBatch-fetch product rows for the winning SKUs; attach the % match.
  6. 6RenderChip + up to 12 cards; weak/overflow matches collapse, or a "no strong matches" state.

What's genuinely not done yet: Vertex AI Multimodal Embeddings

embeddings.py already has a working vertex backend (same interface as local CLIP — swap one config value, embedding.backend: vertex) that calls Vertex AI's multimodalembedding@001 and produces a 1408-dim vector instead of CLIP's 512-dim one. The rest of the pipeline is dimension-agnostic, so this genuinely is a config flip, not a rewrite.

What hasn't happened: it's never been run against production traffic, benchmarked for latency, or compared for embedding quality against local CLIP. The real tradeoff to measure before switching — an API call per query (network latency, per-call cost, but no 577MB model in the image and a much faster cold start) versus a bundled model (larger image, slower cold start, but zero per-query network dependency and zero marginal cost) — is a planned comparison, not a completed migration. Don't read the "coded" status above as "evaluated."

Lessons from a real deployment

Deploying this for real surfaced bugs that only live infrastructure could have — every one of these is documented with its root cause and fix in GCP_SETUP.md, written as a reusable runbook, not just a changelog.

HNSW recall miss

pgvector's default search breadth (ef_search=40) was too narrow for this catalog size and missed the true nearest neighbors on ambiguous queries. Found by comparing exact in-memory search against pgvector for the same photo, fixed with a per-query SET LOCAL hnsw.ef_search = 200.

N+1 seeding

A per-row existence check before insert is fine on localhost but is a separate network round trip per row against remote Cloud SQL — 10k rows took over 20 minutes before a single row committed. Fixed with a bulk SKU fetch + batched insert/update (1000 rows/batch): 9,967 rows in 143 seconds.

torch/torchvision mismatch

Installing torch from the CPU-only index but letting torchvision resolve from default PyPI pulled a CUDA build that didn't match — broke CLIP preprocessing in the deployed container with operator torchvision::nms does not exist. Fixed by installing both from the same index in one command.

Cold starts & CPU starvation

No minimum instance count meant every quiet-period request ate a ~25s cold start loading torch+CLIP; default concurrency (80) let several CLIP calls starve each other for CPU on 2 vCPUs. Fixed with --min-instances=1 and --concurrency=20.

Unindexed full-table listing

/api/products and /api/categories originally fetched the entire 10k-row table (every column) just to slice one page or extract 13 distinct values in Python — 8s and 5.3s respectively. Pushing pagination and DISTINCT down to SQL cut both to sub-200ms.

Local gcloud auth: a dead end

This network's TLS-intercepting proxy issues a root CA that OpenSSL 3.x strictly rejects — no client-side config fixes it. Cloud Shell (browser-based, already authenticated) is the reliable path for this environment; documented so it isn't re-discovered the hard way twice.

Notes on scale

Precomputed index

Catalog embeddings are computed once and cached (or seeded), not on every request. At tens of thousands of SKUs this stays a one-time offline build/seed step, so server startup stays fast.

pgvector is correct here, not a compromise

At ~10k×512, an exact scan is already fast — HNSW's approximation cost (the recall bug above) was a real tradeoff, not a free win. Vertex AI Vector Search would add an always-on index endpoint (real hourly cost) and 30-60min index builds for no benefit at this scale. Revisit past roughly 10M vectors or when sub-10ms p99 at high QPS is a hard requirement.

Dimension-agnostic

512-dim CLIP or 1408-dim Vertex vectors both flow through the same ranking interface — swapping the model changes nothing downstream, only the fingerprint on the cached/seeded index.
