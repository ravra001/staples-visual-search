Request flow — one photo search

The pipeline is identical in both environments; only the providers behind steps 3–5 change.

  1. 1UploadUser picks a photo via the camera icon in the search bar.
  2. 2POST/api/visual-search sends the image bytes to the backend.
  3. 3EmbedImage → feature vector (heuristic, local CLIP, or Vertex AI).
  4. 4RankCosine similarity vs the pre-embedded catalog index. Top-K.
  5. 5HydrateFetch product rows for the winning SKUs from the catalog store.
  6. 6RenderRanked matches drawn with the same product-tile component.

Notes on scale

Precomputed index

Catalog embeddings are computed once and cached, not on every request. At tens of thousands of SKUs this becomes a one-time offline build step (cache vectors to disk / a table), so server startup stays instant.

Brute-force is fine — until it isn't

Cosine over an in-memory matrix is sub-millisecond for thousands of SKUs. Only when the catalog reaches large scale do you graduate to Vertex AI Vector Search / Matching Engine — the ranking interface doesn't change.

Dimension-agnostic

59-dim heuristic, 512-dim CLIP, or 1408-dim Vertex vectors all flow through the same cosine_similarity() / top_k_matches() — swapping the model changes nothing downstream.
