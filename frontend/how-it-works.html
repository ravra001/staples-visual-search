System Explainer

How search-by-photo works

From a user's uploaded photo to ranked products — how the catalog is stored, how images become vectors, how similarity is computed across 10,000 products, and how the newer features (text refinement, Find Similar, Shop the Room) reuse the exact same machinery instead of bolting on separate code paths.

The one idea everything rests on

An embedding is a vector

An embedding turns an image into a list of numbers — a vector — a point in a high-dimensional space. With CLIP (our default model) each image becomes a 512-number vector, and the model is trained so that visually similar images land close together.

So "find similar products" becomes "find the catalog vectors closest to the photo's vector." Closeness is cosine similarity (the cosine of the angle between two vectors: 1.0 = identical, 0 = unrelated). Every vector is L2-normalized to length 1, so a plain dot product equals cosine similarity — one multiply-add per comparison. Every feature on this page — visual search, text refinement, Find Similar, Shop the Room — is a variation on "get a vector, compare it to the catalog's vectors."

The pipeline at a glance

Three phases. The expensive part — embedding 10k images — happens once, offline. Every search is one query embedding plus one vector comparison, whether that comparison runs in a NumPy matrix in RAM (DATA_BACKEND=memory) or as a query inside Postgres (DATA_BACKEND=sql, the pgvector backend this app actually runs on in production).

Phase 1 — Offline prep (run once)

How the catalog is stored. The 10,000 products live in a plain JSON file, backend/data/catalog_abo.json — each entry is just metadata plus a pointer to an image file (no vectors here):

{ "sku": "ABO-B08FHH4RY4",
  "name": "Rivet Alfred Mid-Century Modern Chair",
  "brand": "Rivet", "category": "chairs",
  "price": 129.99, "list_price": 179.99,
  "rating": 4.4, "reviews": 456,
  "image_url": "/images/products/ABO-B08FHH4RY4.jpg" }

The images are files on disk at backend/static/images/products/<SKU>.jpg. Each product has one JSON row and one image file named by its SKU.

Embedding the catalog is a one-time batch job, build_index.py:

  1. Loop every product that has an image file.
  2. Call embed_catalog_item(bytes, name, brand, description) — embeds the image with CLIP (resize 224×224, color-normalize, encode_image() → 512-dim), then fuses in the product's text via CLIP's text tower (same joint space): fused = normalize(0.3 × image_vec + 0.7 × text_vec). A held-out recall eval showed this beats image-only by +8 points recall@1 — text disambiguates visually similar products (e.g. chair vs. stool vs. ottoman) that a photo alone can't. The query stays pure-image (a user only uploads a photo); only catalog vectors are fused.
  3. Stack all 10,000 fused vectors and save index_clip.npz: the SKUs, the (10000, 512) matrix, and a fingerprint that includes the fusion weight (clip:ViT-B-32:laion2b_s34b_b79k:fusion=0.3) — so a config change is detected and a mismatched cache is refused, not silently ranked against.

That .npz is the precomputed search index for the memory backend. For the sql backend, the same already-computed vectors are reused, not recomputed — products_repo_sql.init_and_seed(reuse_vectors_from="data/index_clip.npz") reads that file and bulk-inserts each product's fused and pure-image vectors into Postgres in batches (1000 rows/batch — a naive per-row check was a real N+1 bug: 10k SELECT-then-write round trips against a remote Cloud SQL instance took over 20 minutes; batching turns that into a handful of round trips). At runtime, neither backend ever re-embeds the catalog. Embedding 10k images on CPU takes ~12 minutes — exactly why it's done once and cached (or seeded) ahead of time.

Phase 2 — Server startup

What happens on boot depends entirely on DATA_BACKEND — everything downstream (Phase 3) is written to not care which one is active.

memory

in-RAM matrix, brute-force
  1. Load PRODUCTS (10k rows) into RAM.
  2. Load index_clip.npz, verify its fingerprint matches the current model config (refuse a stale cache rather than silently rank against it), and hold two aligned (10000, 512) matrices: _index_matrix (fused, for ranking) and _index_image_matrix (pure image, for display).
  3. Average each category's vectors into a (13, 512) centroid matrix.
  4. CLIP itself loads lazily on the first search (~6s once, then fast).

sql (what's actually deployed)

Cloud SQL + pgvector, HNSW-indexed
  1. No catalog rows or vectors load into RAM at all — _load_sql_centroids() runs a single 13-row SELECT for the category centroids (precomputed at seed time) and that's it.
  2. Every product row and its two vectors (fused + pure-image) live in the products table, with an HNSW index on the fused embedding column (vector_cosine_ops).
  3. A search never scans a Python list — it's one SQL query, index-accelerated.

HNSW is approximate: its default search breadth (ef_search=40) was found — via a real production bug — to be too narrow for this catalog size and could miss the true nearest neighbors for ambiguous queries. Fixed by raising it to 200 per-query (SET LOCAL, scoped to one transaction). See GCP_SETUP.md for the full story.

Phase 3 — A live photo search

The core pipeline for one uploaded photo, end to end. Everything below it in this section is a variation that reuses these same pieces.

  1. 1UploadUser picks a photo; the browser POSTs it to /api/visual-search.
  2. 2ValidateMust be an image; oversized uploads get a clean 413.
  3. 3OffloadCPU work runs in a threadpool so the server stays responsive.
  4. 4EmbedSame embed_image() as the catalog → a normalized 512-vector q.
  5. 5ClassifyCentroids · q → predicted category + confidence (the "Detected:" chip).
  6. 6RankFused vectors · q — in-memory matmul or a pgvector query, same interface either way; fetches 48 candidates.
  7. 7Score for displayPure-image vectors · q, computed only for those 48 already-ranked items.
  8. 8HydrateBatch-fetch those product rows; attach the display % match.
  9. 9RenderChip + up to 12 cards; the rest (and anything below the match threshold) collapse behind one expander.

Ranking vs. display: two scores, on purpose

A pure-image query naturally scores lower against a fused (image+text) catalog vector than against a pure-image one — CLIP's image and text embeddings don't perfectly overlap (the "modality gap"), and blending in 70% text pulls a catalog vector toward text-space. Showing that fused number directly made a near-perfect match read as a discouraging ~60%.

So the two jobs are split: which products appear (and their order) always comes from the fused score — that's what the recall eval validated. What number is shown — and what the match-threshold gate reacts to — is a separate pure-image cosine, computed only for the 48 already-chosen candidates (cheap: 48 dot products, not a second full ranking pass). A genuine match reads ~85–100%, same scale as before fusion existed.

48 fetched, 12 shown, on purpose: the backend always fetches 48 candidates so sorting and price-filtering (below) have real material to work with — reordering the same 8 tiles by price wasn't a useful feature. The results grid shows the top 12 by default; the rest fold into the same "show more matches" expander that below-threshold items already use.

Text-refined queries — "but in black"

CLIP has a text tower as well as an image tower, in the same joint 512-dim space — already used to fuse catalog vectors in Phase 1. Refinement reuses it on the query side: type "but in black" and that phrase gets embedded and blended into the query vector, then the catalog is re-ranked against the blended vector.

Why refinement is a two-stage, pool-constrained rerank — not a fresh whole-catalog search

The first version blended the text vector in and searched the entire catalog with it. That broke in production: a bare color word like "black" embeds close to generic solid-color/swatch imagery in CLIP's text space, and blending even 30% of it in was enough to jump a search that correctly found real wall clocks onto unrelated fabric swatches instead — found via manual testing, not a hypothetical.

Fixed with two stages: first rank a pool of 100 items using the unblended query (the normal search — guarantees the pool is topically relevant), then re-rank only that pool using the blended (image + 30% text) vector. A refinement can now only reorder items that were already legitimate matches — it can never introduce an unrelated one. (REFINE_IMAGE_WEIGHT = 0.7, REFINE_POOL_SIZE = 100 — both empirically tuned, not derived; a wider pool was tested and made the color-swatch failure mode come back.)

On DATA_BACKEND=sql, the second stage deliberately does not run a second pgvector query — Postgres's planner could choose the (approximate) HNSW index for a WHERE sku IN (...) ORDER BY <=> query and silently under-return results. Instead the pool's ~100 vectors are fetched once and reranked in NumPy — exact, small, and identical in behavior to the in-memory backend.

Category classification always uses the unblended vector — a color refinement shouldn't change what category the photo is classified as, only which items of that category rise to the top. And refinement isn't only for an uploaded photo: Find Similar (below) supports the identical refine flow, sourced from a stored product's vector instead of a fresh upload.

Price-intent text ("cheaper", "under $50") — sort, not search

Why price never goes through CLIP

CLIP was trained on image/caption pairs — it has no grounding for a concept like "price." Verified directly: sending "cheaper" through the same blend-and-rerank path as "but in black" returned nearly the identical set of items, with no price trend at all. Whatever embedding "cheaper" produces, it isn't one that means "less expensive."

So price-intent phrases are pattern-matched client-side (_parsePriceIntent) and handled as a plain sort/filter over the already-fetched 48 results — zero network calls, and always correct, because price is exact data already in hand, not something to approximate. "under $50" captures the number and applies it as a real filter; a compound query like "cheaper black one" splits the price phrase out, applies it as a sort, and still sends the leftover "black" through as a genuine CLIP refinement — both mechanisms fire, each doing only the job it's actually good at.

Find Similar — query FROM the catalog, not a fresh upload

Every product already has a stored vector — its own catalog image was embedded in Phase 1. "Find similar" on any product card or product page reuses that stored vector as the query, with no re-embedding call: GET /api/products/{sku}/similar fetches that product's pure-image vector and runs it through the identical rank/refine machinery a photo upload uses. This is also why enabling text refinement here ("find similar, but in black") was a small change, not a new feature — the refinement code never cared where the query vector came from.

Shop the Room — one photo, one match per item

Every other search here has the same output shape: photo in, a ranked pile of similar things out. Shop the Room changes that shape: upload a photo of a room and get back one best-matching product per distinct furnishing detected — the sofa, the rug, the lamp, the wall art — with a running total and one "Add all to cart" button, instead of eight near-duplicates of whichever object was most visually prominent.

  1. The photo is split into a small tile grid — the whole image plus a 2×2 crop (5 tiles total, kept intentionally small: on the SQL backend each tile costs one network round trip, and a wider 3×3 sweep measured ~30s cross-region in testing versus ~1-3s same-region).
  2. Each tile is embedded and classified independently, then ranked within its predicted category — the exact same embed_image → classify → rank pipeline as a normal search, called once per tile.
  3. Unlike a normal search, a tile's classification does not need to clear the usual confidence threshold — that threshold is calibrated for "should we auto-scope a whole clean photo," and a small cropped tile is inherently less certain even when its guess is right (verified: a lamp tile classified at only 36% confidence still found the exact correct lamp at 77% match). What does gate a tile is whether its top product match clears the normal match threshold — a blank wall or floor tile just won't find anything above that bar and is silently skipped.
  4. If two tiles land on the same category, only the higher-scoring one survives. Results are capped at 6 distinct categories, sorted by score.

Crop-to-search — the multi-object problem, without a new model

A photo with more than one object (a room shot with a sofa and a lamp) embeds as an arbitrary blend of everything in frame. Crop-to-search lets the user drag a box over their uploaded photo; the selection is cropped client-side on a <canvas> — correctly mapping through the image's object-fit:contain letterboxing rather than assuming a 1:1 pixel mapping — and the crop is re-submitted through the exact same /api/visual-search endpoint as a normal upload. No detector model, no new infrastructure: it produces a new "photo" and lets the existing pipeline do the rest. Pointer Events (not raw mouse events) drive the drag, so this works with touch on a tablet as well as a mouse.
